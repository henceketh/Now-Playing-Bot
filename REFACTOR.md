# Разбор и результат рефакторинга

Исходный проект состоял из двух независимых Node.js-приложений: Telegram-бота и Express backend. В backend на 450 строк были смешаны OAuth, запись токенов, playback, тексты, YouTube, запуск shell-команды и маршруты. Бот обращался к backend только за файлом, используя фиктивные URI и название. Поиска по тексту inline-запроса не было, несмотря на описание в README.

Сохранена исходная идея: один подключённый Spotify-аккаунт, разрешённые Telegram-пользователи и два процесса. Разделение проведено по ответственности; фабрики сервисов принимают настройки и заменяемые зависимости. Нет новой сборки, базы данных, framework или очереди заданий.

## Исправлено

| Исходная проблема | Изменение |
| --- | --- |
| Любой пользователь мог выполнить `/god` | Обязательный allowlist, проверяемый и командой, и inline handler |
| Фиктивный `track_uri`, названия из HTTP-заголовков | Реальные `id`/`uri` и Unicode metadata из playback JSON |
| Каждый запрос повторно скачивал файл | Стабильный кэш по URI и объединение одинаковых активных загрузок |
| Песня могла смениться между metadata и скачиванием | Проверка ожидаемого ID, ответ `409` вместо неверного кэша |
| Inline handler ждал весь yt-dlp и не отвечал при ошибке | Сразу возвращается ссылка при холодном кэше, загрузка идёт в фоне; ошибки имеют явный ответ |
| Результаты Telegram могли кэшироваться между пользователями | `is_personal: true`, короткий срок кэша |
| Нет каталога, ошибки stream не обрабатывались | Создание каталога, pipeline, временный файл, атомарный rename и cleanup |
| Параллельная запись пользователей теряла ID | Очередь операций и атомарная JSON-запись |
| Отсутствующий файл не отличался от повреждённого | Только `ENOENT` означает начальное состояние; ошибки JSON явно сообщаются |
| Client credentials grant перезаписывал пользовательский токен | Единственный OAuth Authorization Code Flow для playback |
| Refresh работал по фиксированному таймеру и не сохранял токены | Проверка срока, один refresh для параллельных запросов, сохранение нового токена и ротации refresh token |
| OAuth callback без state | Сравнение state с cookie браузера, отказ при несовпадении |
| Токены и client secret выводились в логи | Секретные данные не логируются, ответы ошибок содержат безопасные сообщения |
| Токены и runtime-файлы отслеживались Git | Убраны из индекса, добавлен `.gitignore`; локальные файлы сохранены |
| Пустые item/обложки и эпизоды вызывали исключения | Нормализация playback с явным состоянием «нет песни» |
| yt-dlp запускался через shell, без лимита времени | `execFile`, отдельные аргументы, лимиты времени/размера/параллельности |
| После сбоя скачивания оставались промежуточные файлы | Удаляется весь отдельный временный каталог |
| Тексты требовали web token на каждый запрос, Genius был отключён | Необязательные провайдеры, повторное использование токена до expiry, рабочий fallback Genius |
| HTTP/OAuth зависели от cwd и незавершённых зависимостей | Явные пути, валидация настроек, единый workspace и lockfile, рабочие start scripts |

## Что делать дальше по мере необходимости

«Все возможные проблемы» нельзя доказательно исключить. Полезнее покрыть границы системы и добавлять сложность по наблюдаемым сбоям.

1. **Перед реальным запуском:** проверить собственные ключи, redirect URI, inline mode, доступность MP3 через публичный HTTPS URL и наличие yt-dlp/ffmpeg. Если реальные credentials были в истории Git — отозвать их. Backend держать приватным.
2. **При долгой работе:** установить лимит диска и срок хранения кэша; удалять остатки после аварийного завершения. Проверять свободное место и число ошибок загрузки. Автоматическое удаление требует решения, как долго должны жить ранее отправленные ссылки.
3. **При частых запросах:** короткий кэш playback на 1–2 секунды и cooldown по `Retry-After`, чтобы не расходовать Spotify/YouTube quota повторными запросами. У бота уже есть объединение загрузок одного трека и предел параллельных скачиваний.
4. **При неправильных песнях:** сравнивать нормализованные title/artist и длительность нескольких результатов YouTube, дать владельцу ручной override. Первый результат сейчас не гарантирует оригинал.
5. **При нескольких процессах или аккаунтах:** заменить JSON на SQLite/Postgres, связать Telegram ID с собственными Spotify credentials, вынести загрузки в общую очередь. Текущий allowlist управляет доступом к одному общему аккаунту.
6. **Если тексты важны:** учитывать, что Spotify web lyrics endpoint не является стабильным публичным API, а Genius HTML может измениться. Сейчас сбой текстов не ломает playback. Для стабильности лучше отдельный поддерживаемый источник.
7. **При постоянной эксплуатации:** запускать процессы под supervisor, добавить health checks и структурированные логи со стадией операции и кодом ошибки; не записывать токены, cookies или URL с API-ключами. На SIGINT/SIGTERM HTTP-сервер закрывается; отдельный worker понадобится, если нужна гарантированная отмена активного subprocess при остановке.

## Проверка выполненной работы

На Node.js 22 проверены 25 тестов (`npm test`), включая реальные локальные HTTP-запросы к Express. `npm audit` на установленном lockfile: 0 известных уязвимостей. Проверяются сохранение пользователей при конкуренции, дедупликация скачиваний, cleanup потоков и subprocess, токены и OAuth, Unicode metadata, пауза/пустой playback, смена трека, rate limits и немедленные inline-ответы.

Настоящие Spotify/YouTube/Telegram запросы не выполнялись: пользовательские credentials не предоставлены. yt-dlp и ffmpeg не обнаружены в PATH на машине проверки. Реальный end-to-end запуск остаётся ручной интеграционной проверкой по инструкции README.

Контракты сверены с [Spotify OAuth](https://developer.spotify.com/documentation/web-api/tutorials/code-flow), [Spotify Playback State](https://developer.spotify.com/documentation/web-api/reference/get-information-about-the-users-current-playback) и [Telegram inline API](https://core.telegram.org/bots/api#answerinlinequery).
